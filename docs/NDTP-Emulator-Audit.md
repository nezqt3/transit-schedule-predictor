# Разбор официального NDTP-эмулятора v1.0

Проверен предоставленный архив `ndtp-telemetry-emulator.tar`, документация
[`Emulator-and-Telematic-Packets-Specification.md`](Emulator-and-Telematic-Packets-Specification.md),
запущенный образ и реально отправленные TCP-пакеты. Архив — Docker/OCI-образ,
созданный 11 сентября 2026 года. Приложение внутри — Spring Boot JAR
`ndtp-telemetry-emulator-1.0.0-SNAPSHOT.jar`, запускаемый на Java 17.

## Что находится внутри

- В JAR есть классы REST-конфигурации, TCP-клиента, сборки пакетов NDTP,
  `RandomTelemetryGenerator` и определения 23 типов телематических ячеек.
- Среди ресурсов приложения есть только `application.yml` с портом 18080 и
  настройками логирования. Файлов расписания, GTFS, CSV с маршрутами,
  геометрии линий и справочника остановок в образе нет.
- `GET /api/cells` показывает навигацию, датчики, CAN, двери, пассажиропоток,
  RFID и прочую телематику. Типа ячейки «маршрут» или «остановка» нет.
  `Nav00.track` — счётчик пройденного расстояния, не ID маршрута.
  Наличие произвольного текстового `Reg09.name` не задаёт маршрутной схемы.

## Как он работает

После запуска `GET /api/config` вернул `units: []`: до `POST /api/config`
телеметрия не идёт. В конфиге задаются адрес TCP-приёмника, `unitId`, интервал
или cron, режим `autoGenerate` и список ячеек. Для каждого устройства
эмулятор открывает отдельное TCP-соединение, отправляет handshake и затем
пакеты с навигационной ячейкой. При `autoGenerate: true` и пустом `cells`
реальный пакет содержит типы `0, 8, 16, 2, 10` — навигацию, топливо,
температуру, внутренние датчики и CAN. Все эти типы наш парсер декодирует.

В наблюдённом официальном пакете флаги NPL равны `0x0000`, хотя поле CRC
заполнено. Наш парсер такие кадры принимает; проверку CRC протоколом флагов
этот образ не запрашивает. Собственный январский NDTP-replay выставляет
`0x0002`, то есть его кадры отличаются в этом месте, но также принимаются
нашим сервером.

## Маршруты и физическая достоверность

Автогенератор создаёт координаты около Москвы и меняет их на каждом тике.
У него нет дорожного графа, остановок, расписания, номера маршрута или
сведений о пробках. Нарисованная для такого устройства линия может быть
только следом уже полученных GPS-точек.

Для одного тестового `unitId` при интервале 5 секунд измерены следующие
последовательные пакеты:

| Время Unix | `speedAvg`, км/ч | GPS-путь за 5 с | Рост `track`, м |
| --- | ---: | ---: | ---: |
| 1790452627 | 39 | — | — |
| 1790452632 | 42 | 3,55 м | 336 |
| 1790452637 | 50 | 3,61 м | 400 |
| 1790452642 | 56 | 3,88 м | 448 |

По GPS эти шаги соответствуют примерно 2,6–2,8 км/ч, несмотря на
переданную скорость 42–56 км/ч. `track` также растёт намного быстрее
геометрического перемещения. При интервале 1 секунда GPS-шаги были похожего
порядка, около нескольких метров. Это наблюдение относится к синтетическому
официальному генератору: его скорость, `track` и координаты нельзя считать
согласованной записью настоящей поездки и использовать для проверки ETA.

## Сравнение с нашей системой

| Компонент | Что делает сейчас | Следствие |
| --- | --- | --- |
| Официальный эмулятор | Посылает синтетические NDTP-пакеты | Проверяет TCP, парсер, WebSocket и отображение терминалов; фактических рейсов нет |
| Live NDTP в Backend | `NdtServer` передаёт событие в `TelemetryService`, который хранит состояние и рассылает его | По одному пакету прогноз автоматически не запускается |
| Live-карта | Рисует текущие позиции и до 150 последних точек выбранного терминала | Синяя линия — GPS-след, не плановый маршрут |
| Январский NDTP-replay | Читает `traffic.csv` и передаёт реальные исторические GPS-точки по TCP | Проверяет транспортный канал с реальными траекториями |
| Январская вкладка | Отдельно читает CSV через `/api/v1/replay/fleet` и вызывает `/api/v1/replay/predict/{sample_id}` | Маршруты и прогноз здесь строятся из CSV, а не из живого NDTP-потока |

Демонстрационные `unitId` официального конфига (`1166336`, `1166789`) не
встречаются среди 30 устройств январского `traffic.csv`. Даже при наличии
расписания их нельзя автоматически сопоставить с январскими рейсами.
Сам NDTP-пакет не содержит `tr_id`, целевую остановку, плановое время её
прибытия и `cur_dev_s`. Для прогноза на горизонте 10–15 минут эти сведения
нужны из отдельного планового/диспетчерского источника.

## Найденная ошибка совместимости

До этой проверки парсер поддерживал пять автоматически отправляемых типов
и умел пропустить только `Lls15`. При добавлении в официальный конфиг,
например, `G6CellIrma04` пакет целиком отклонялся с ошибкой «неизвестный тип
ячейки: 4», поэтому терялась и корректная GPS-точка. Реальный пакет с этой
ячейкой воспроизвёл ошибку. Размеры всех остальных ячеек измерены по
пакетам запущенного образа; теперь парсер пропускает их по фиксированным
размерам и сохраняет навигацию. Неизвестные типы за пределами каталога v1.0
по-прежнему отвергаются: у ячейки NDTP нет поля длины, безопасно пропустить
её без схемы нельзя. Версия handshake теперь читается из пакета.
Контрольный пакет со всеми 22 дополнительными типами (750 байт вместе с NPL)
разобран успешно: навигация и четыре поддерживаемых вида датчиков сохранены.

## Практический вывод

Официальный образ следует использовать для проверки протокола и доступности
дашборда. Реалистичные маршруты и точность ML следует проверять на январской
записи с её расписанием и GPS. Для общего рабочего потока нужно связать
`unit_id` с рейсом и планом, получать текущее отклонение без будущих данных,
выбирать целевую остановку в окне `(T+10 мин, T+15 мин]` и запускать
ML-прогноз при поступлении телеметрии. Синтетическому устройству без
расписания нельзя правдиво назначить остановки или задержку.
