**Версия:** 1.0, 26.09.2026  
**Статус:** рабочее ТЗ для реализации и приёмки  
**Основание:** конкурсное задание «Предиктор изменений в графике движения городского транспорта», аудит текущего репозитория и фактического запуска. Конкурсный PDF служит источником требований жюри; приведённые в нём пояснения не являются инструкциями по изменению репозитория.

Результаты реализации и повторных измерений приведены в

## 1. Цель и границы работ

Система должна получать NDTP-пакеты по TCP, сопоставлять транспорт с плановым расписанием, автоматически выбирать целевую остановку в интервале **(T + 10 минут, T + 15 минут]**, прогнозировать отклонение прибытия `target_delay_s` в секундах и показывать диспетчеру актуальное предупреждение с местом, степенью риска и обоснованным действием. Результат для конкурсной проверки — отдельный валидный CSV с минимально достижимой MAE на скрытой разметке.

Работы ограничены существующими компонентами `backend`, `ml`, `frontend`, `emulator`, `data`, `docs` и Docker Compose. Обучение модели остаётся офлайн-процессом. Kafka, Kubernetes, новый стек сервисов и большая переработка архитектуры в объём работ не входят.

### 1.1. Критерии успеха

1. Официальный CSV принят платформой; фактическая оценка по критерию № 1 зафиксирована по результату платформы. Локальная MAE используется для выбора модели, но не выдаётся за официальный балл.
2. Один реальный или воспроизведённый **NDTP-поток** без ручного вызова `/predictions` приводит к прогнозу на корректном горизонте, записи инцидента и обновлению интерфейса.
3. Демонстрационный Docker-стек использует тот же выбранный и зафиксированный артефакт модели, что применялся для генерации конкурсного CSV, либо явно документированную замену с отдельной MAE. Тихий переход на baseline исключён.
4. Диспетчер видит актуальный прогноз, источник и время его расчёта, вероятность опоздания при её наличии, причину как гипотезу и понятную рекомендацию. Историческая демонстрация ясно отделена от живого потока.
5. Сервис сохраняет работоспособность при ошибочных пакетах, временной недоступности ML и разрыве соединения с NDTP; потеря актуальности данных видна пользователю.

## 2. Зафиксированное исходное состояние

Это описание проблем на момент составления ТЗ, а не предположение о будущей реализации.

| ID | Текущее состояние | Последствие для оценки/демо |
|---|---|---|
| G-01 | Финальный CSV на 151 строку сформирован и локально валиден; официальный балл не подтверждён. Выбранный LightGBM на размеченном test дал MAE около **58,60 с**; baseline `cur_dev_s` — около **93,36 с**. | Нельзя обещать конкретный балл критерия № 1. |
| G-02 | Compose по умолчанию запускает `MODEL_NAME=baseline`; локальные веса игнорируются Git и не поставляются как обязательная часть чистого запуска. | Жюри может увидеть другой алгоритм, чем использован в отправленном CSV. |
| G-03 | NDTP-пакет обновляет состояние машины, но не запускает расчёт прогноза. Вычисление выполняется через ручной запрос API. | Основной поток NDTP → ML → интерфейс разорван. |
| G-04 | Для ручного прогноза вызывающий код обязан передать `cur_dev_s`, остановку и плановое время; автоматического выбора целевой остановки и надёжного вычисления текущего отклонения нет. | При потоке эмулятора нет достаточных данных для прогноза. |
| G-05 | Исторический replay и живой NDTP используют разные часы. При сдвиге времени пакетов расписание не сдвигается согласованно. | Окно 10–15 минут не воспроизводится на реальном потоке. |
| G-06 | WebSocket выдаёт `vehicle_snapshot`, `vehicle_update`, `heartbeat`; маршрутов и событий инцидентов нет. | Диспетчер не получает предупреждение в реальном времени. |
| G-07 | Цвета и статусы в интерфейсе частично отражают факт телеметрии и порог задержки, а не прогнозный риск; нет подтверждённой вероятности, причины и рекомендации. | Недостаточное покрытие BI-критерия. |
| G-08 | Исторический endpoint передаёт будущий `actual_delay_s` в данных воспроизведения до наступления события. | Нарушается достоверность демонстрации; нельзя использовать этот путь как доказательство реального прогнозирования. |
| G-09 | Инструкции запуска и статический OpenAPI содержат устаревшие сведения; часть сырого датасета отслеживается Git. | Чистый запуск и проверка результатов трудно воспроизводимы. |

Локальная MAE — контрольный ориентир для неизменного размеченного набора, а не гарантированное значение на скрытом `validate`. Совпадение файлов `test/traffic.csv` и `validate/traffic.csv`, пересечение транспортных средств и наличие факта в расписании train/test создают поверхность возможной утечки; прямое использование скрытых ответов в текущем CSV аудитом не доказано. Проверки ниже должны исключить такую утечку конструктивно.

## 3. Функциональные требования

### 3.1. Конкурсная модель, данные и артефакты

**FR-ML-01 — выбор и фиксация модели (P0).** Для каждого кандидата сохранять локальную MAE на временно отделённом размеченном наборе, MAE baseline и параметры запуска. Перед отправкой выбрать одну модель, зафиксировать код генерации, список признаков, версию зависимостей и контрольные суммы артефактов. Результат платформы записывать отдельно после загрузки CSV. Не выбирать модель повторно по скрытой оценке так, будто это независимая валидация.

**Приёмка:** итоговый `submission.csv` содержит ровно все `sample_id` из шаблона по одному разу, строго две колонки `sample_id;prediction` с разделителем `;`, конечные числовые значения в секундах и не содержит целевую разметку или дополнительные поля; сохранены команда генерации, хеш файла и ответ платформы. Если официальный ответ ещё недоступен, статус указывается «неизвестен», без рассчитанного балла.

**FR-ML-02 — единая модель офлайн и в сервисе (P0).** Модель, использованная для выбранного CSV, доступна в контейнере ML с тем же feature pipeline, порядком признаков и конфигурацией. Демо-конфигурация Compose явно задаёт выбранную модель вместо текущего дефолта `MODEL_NAME=baseline` и проверяет хеш артефакта при старте. `GET /health` сообщает имя модели, версию и состояние загрузки. При отсутствующем или повреждённом артефакте сервис завершает загрузку с явной ошибкой либо сообщает `unhealthy`; подмена на baseline без явной настройки запрещена. Baseline остаётся отдельным явно выбираемым режимом.

**Приёмка:** на одном и том же наборе входных точек вывод офлайн-скрипта и `POST /predict` совпадает с допуском `1e-6` с при одинаковых числовых типах. На ранее использованных 353 размеченных test-точках повторно измеренная MAE объяснимо совпадает с зафиксированной ориентирной MAE 58,60 с; любое отклонение выше 0,01 с требует анализа версии данных/модели. Тестовый набор не монтируется в боевой ML-контейнер ради этой проверки.

**FR-ML-03 — причинность признаков (P0).** Для точки `(tr_id, T)` разрешены только входы, доступные на `T`: плановое расписание, последние уже подтверждённые прибытия и телеметрия с `event_time ≤ T` и `receive_time ≤ T`, если `receive_time` задан. Фактическое время целевой и последующих остановок, `target_delay_s`, `target_class`, метки после `T`, строки из будущего той же поездки и сведения replay о будущих событиях в признаки не попадают. При формировании `validate` и в runtime расписание читается через явный список только плановых полей: `time_fact_begin` из train/test не может попасть в признаки даже при совпадении транспорта или остановки. Логика признаков для обучения и сервиса общая либо побайтно/численно проверена на паритет.

**Приёмка:** для нескольких точек на границах горизонта составлен протокол происхождения каждого признака; автоматическая проверка на инъекцию пакета с `event_time > T` и будущего факта остановки доказывает неизменность прогноза. При удалении всех будущих строк результат не меняется. Источники `cur_dev_s` и времени прибытия протоколируются.

**FR-ML-04 — регрессионная цель (P0).** Основной результат `prediction` — отклонение в секундах, знак сохраняется (`>0` опоздание, `<0` опережение). Основная метрика — MAE. Вероятность риска является дополнительным выходом и не заменяет регрессию.

**FR-ML-05 — вероятность опоздания (P1).** Отдельно оценивать `p_late` для события `target_delay_s ≥ 120 с` на временной валидации, калибровать вероятность и публиковать её вместе с версией модели калибровки. Допустимая реализация: вспомогательная классификация по причинным признакам или калибровка распределения ошибки регрессора. Значение `0.9`, полученное простым сравнением прогноза с порогом, вероятностью не считается.

**Приёмка:** представлены Brier score и калибровка по бинам на отложенном периоде, определён порог опоздания и версия калибровки. При отсутствии валидированной вероятности поле равно `null`, а интерфейс показывает «вероятность не рассчитана».

### 3.2. Приём NDTP и построение точки прогноза

**FR-RT-01 — приём телеметрии (P0).** Backend слушает конфигурируемый TCP-порт NDTP, разбирает фреймы с проверкой длины/типа/контрольных полей, нормализует пакет в единый объект и обновляет состояние терминала. Ошибочный пакет регистрируется и пропускается без падения сервера и без остановки других соединений. Повторные и неупорядоченные пакеты не должны возвращать состояние транспорта или прогноз в прошлое.

**Приёмка:** поток с корректными, неполными, ошибочными, повторными и пришедшими не по порядку пакетами продолжает обработку; количество принятых/отброшенных пакетов видно в логах или метриках; для каждого обновления указаны `unit_id`, `event_time`, `receive_time`, координаты и достоверность GPS.

**FR-RT-02 — связь терминала с рейсом (P0).** Для `unit_id` задаётся или определяется актуальный `tr_id`, рейс/маршрут и план остановок. Если соответствие неоднозначно или отсутствует, транспорт остаётся видимым как телеметрия со статусом `schedule_unmatched`; система не выдаёт фиктивный прогноз. Маппинг загружается из явного конфигурационного источника и отражается в документации запуска.

**FR-RT-03 — целевая остановка (P0).** На каждом моменте расчёта `T` выбирать **первую** остановку данного рейса с плановым прибытием строго позже `T+600 с` и не позже `T+900 с`. Использовать единое часовое правило и явные UTC-offset/timezone при чтении CSV и NDTP: для исходных timestamp без зоны задать документированную зону источника и только затем приводить к UTC. При отсутствии остановки возвращать состояние `no_target_in_horizon`, не подбирать ближайшую за пределами окна.

**Приёмка:** проверки на `T+600 с` (исключена), `T+601 с` (включена), `T+900 с` (включена), `T+901 с` (исключена), а также два кандидата в окне (выбран более ранний). Одно и то же правило действует для тренировочного набора, сервиса и replay.

**FR-RT-04 — текущее отклонение (P0).** `cur_dev_s` рассчитывается по последней **подтверждённо пройденной** остановке и её плановому прибытию либо поступает из явно указанного доверенного источника. Определить правило подтверждения: геозона остановки с проверкой направления/последовательности рейса, допустимое время и качество GPS; одиночный проезд рядом не считать прибытием. При недостатке данных источник равен `unavailable`: нельзя незаметно подставлять `0` или значение из будущего. Для офлайн-точек разрешено использовать предоставленное в датасете `cur_dev_s` с пометкой `point_input`.

**Приёмка:** в ответе и техническом журнале доступны `current_delay_s`, `current_delay_source`, `last_confirmed_stop_id`, время подтверждения или причина отсутствия. Сценарии «нет истории», «ложное приближение к остановке», «потеря GPS» не дают выдуманного отклонения. Если выбранная модель требует признака и он недоступен, система выдаёт явный `insufficient_data` либо использует отдельно оцененный fallback с собственной версией и MAE.

**FR-RT-05 — автоматический оркестратор (P0).** После нормализации нового пакета backend обновляет историю, проверяет соответствие рейсу, выбирает остановку, формирует причинные признаки, обращается к ML, сохраняет последний прогноз, оценивает инцидент и публикует событие WebSocket. Частота прогноза на машину ограничена настраиваемым интервалом и/или изменением целевой остановки; параллельно допускается не более одного активного расчёта на машину. Входной поток не блокируется ожиданием ML.

**Приёмка:** после запуска тестового NDTP-потока без обращения к ручному endpoint появляются `GET /api/v1/predictions/{tr_id}/latest` и событие `prediction_update`. При непрерывной телеметрии периодичность ML-вызовов не выше установленного лимита, а новый прогноз не перезаписывается более старым результатом.

**FR-RT-06 — согласованные часы replay (P0).** У воспроизведения есть один документированный логический момент `T`. Пакеты, расписание, последний подтверждённый факт и отображаемое время преобразуются согласованно; ускорение меняет темп подачи, но не математический горизонт 10–15 минут. Исторический режим обозначается как replay, а не как текущая городская обстановка. Отдельный табличный `/replay/predict` может остаться инструментом сравнения модели, но не считается доказательством работы NDTP-контура.

**Приёмка:** при скоростях 1× и ускоренной подаче для идентичной логической точки выбирается одинаковая целевая остановка и одинаковое окно в **логическом времени**; у каждого ML-запроса в истории нет пакетов из будущего. Проверка проводится на потоке через TCP-порт backend.

### 3.3. Прогнозы, инциденты и API

**FR-API-01 — данные прогноза (P0).** Последний прогноз содержит как минимум `tr_id`, `unit_id`, момент прогноза `T`, фактическое время вычисления `produced_at`, `target_stop_id`, плановое прибытие, `predicted_delay_s`, расчётное прибытие, источник/значение текущего отклонения, модель/версию/хеш артефакта, источник данных (`live`/`replay`/`manual`), статус свежести и необязательную `p_late`. Значения задержки измеряются в секундах. Ручной endpoint сохраняется для диагностики, но его результат помечается `manual`.

**Приёмка:** `GET /api/v1/predictions` и `GET /api/v1/predictions/{tr_id}/latest` возвращают эти поля; старый ответ не заменяет новый по `T`; клиент может отличить `fresh`, `stale`, `unavailable` и источник результата.

**FR-API-02 — события WebSocket (P0).** `WS /api/v1/ws` после авторизации выдаёт начальное состояние либо клиент получает его REST-запросами, затем события `vehicle_update`, `prediction_update`, `incident` и heartbeat. Каждое событие включает `type`, `data`, `event_id` и `emitted_at`; при переподключении клиент повторно читает REST-снимок, чтобы не терять актуальное состояние.

**Приёмка:** создание прогноза/инцидента через NDTP появляется на открытом dashboard без перезагрузки; после разрыва и переподключения состояние совпадает с REST. События старше уже показанного `T` игнорируются клиентом.

**FR-API-03 — инциденты (P0).** Реализовать `GET /api/v1/incidents`, `GET /api/v1/incidents/{incident_id}` и хранение актуальных инцидентов. Новый инцидент возникает по конфигурируемому правилу риска. Повторные прогнозы одной машины для той же целевой остановки обновляют один инцидент; при нормализации риска или смене цели он закрывается/завершается, а история остаётся доступной в рамках выбранной схемы хранения. В карточке обязательны ссылка на прогноз, транспорт, рейс/маршрут, участок «последняя подтверждённая остановка → целевая», прогноз в секундах, категория риска, время и статус.

**FR-API-04 — риск и объяснение (P0/P1).** Предусмотреть категории `low`/`medium`/`high` с версионированной и настраиваемой политикой. На P0 допустим порог по прогнозу как **эвристический риск** (`risk_source=threshold`) без выдуманной вероятности. На P1 при наличии калиброванного `p_late` политика использует вероятность (`risk_source=calibrated_probability`). Дефолтные пороги допускается установить после оценки ложных тревог на временном test; они публикуются в конфигурации. Причина инцидента (`cause`) формулируется как гипотеза из наблюдаемых признаков, например «длительная стоянка» или «низкая скорость на участке», с указанием наблюдения, а не как доказанный внешний фактор вроде ДТП. Рекомендация привязана к категории риска и фактическому контексту; если данных мало, текст сообщает об этом.

**Приёмка:** карточка не показывает числовую вероятность, если модель её не выдала; при одинаковых прогнозных данных политика выдаёт одинаковый риск; причина и рекомендация не ссылаются на будущее или отсутствующий датчик.

### 3.4. Интерфейс диспетчера

**FR-UI-01 — единый рабочий экран (P0).** На карте и в списке транспорта показывать последнее положение и отдельную визуальную кодировку **прогнозного риска**: зелёный, жёлтый, красный. Состояние связи/GPS отображать собственным индикатором, чтобы оно не выдавалось за риск опоздания. Показывать время последнего пакета и прогноза, подсвечивать устаревшие данные.

**FR-UI-02 — карточка инцидента (P0).** По инциденту диспетчер видит транспорт, маршрут/рейс, плановую и расчётную дату-время целевой остановки, предсказанное отклонение в секундах/минутах, участок маршрута, риск, `p_late` при наличии, наблюдаемые признаки/гипотезу причины и действие. Для P0 допускается шаблонная рекомендация на основе явно названного правила; P1 требует проверки полезности текста на типовых сценариях.

**FR-UI-03 — live/replay и доступность будущих фактов (P0).** Режим данных обозначен постоянно на экране. В live разрешены только известные на момент `T` факты. В replay фактический исход остановки открывается клиенту **после** наступления события в логическом времени; сервер не должен заранее отправлять `actual_delay_s` будущих точек в общем ответе. Метрики с известными метками доступны отдельно в диагностическом режиме и явно помечены как ретроспективные.

**Приёмка UI:** диспетчер находит красный инцидент на карте и в списке, раскрывает карточку и понимает требуемое действие за не более 5 секунд при демонстрационном сценарии; разрыв WebSocket переводит обновления в видимый статус ожидания и после восстановления синхронизирует данные. Фронтенд проходит сборку.

### 3.5. Запуск, надёжность и производительность

**FR-OPS-01 — воспроизводимый Docker (P0).** Из чистого checkout при наличии отдельно предоставленного и проверенного модельного артефакта и входных CSV команда `docker compose up --build` запускает backend, ML, frontend и необходимые зависимости. Отдельные образы backend и ML используют Python 3.12+. Конфигурация адресов, портов, паролей и путей задаётся env-переменными; `.env.example` перечисляет обязательные значения. Большие исходные данные и веса передаются как внешние артефакты с контрольными суммами, а не случайно зависят от файлов разработчика.

**FR-OPS-02 — деградация (P0).** При недоступном ML backend продолжает принимать NDTP и отдавать состояния транспорта; существующий прогноз помечается `stale`, новый не изобретается. При разрыве NDTP виден последний известный транспорт и возраст данных; восстановление соединения возобновляет обновления. Ошибочный пакет не влияет на остальных клиентов. При недоступной БД сервис возвращает явную ошибку для зависимых операций и восстанавливается после подключения; критические ограничения текущего режима хранения описаны.

**FR-OPS-03 — измерение скорости (P1).** Измерять от поступления подходящего NDTP-пакета до WebSocket-обновления интерфейса: p50/p95/p99, ML latency, количество вызовов модели на машину, очередь, отброшенные пакеты и время холодного старта. Целевая нагрузка для приёмки: 100 активных машин, по одному пакету каждые 15 секунд на машину в течение 10 минут, CPU-инференс без GPU. Цель — p95 сквозной задержки не выше **2 с**, без монотонного роста очереди и без потерь корректных пакетов при этой нагрузке. Результаты указываются с характеристиками машины; если цель не достигнута, фиксируются фактические цифры и узкое место.

**FR-OPS-04 — эмулятор организаторов (P0).** Подготовить конфигурацию сопоставления терминалов, актуального плана и времени для доступного официального эмулятора. Его TCP-поток должен пройти через тот же backend и ML без приватных ручных вызовов. Если эмулятор не предоставляет расписание, явный тестовый план создаётся как отдельный демо-артефакт; он не маскируется под реальное расписание города.

**Приёмка:** для минимум двух терминалов в NDTP-потоке получены автоматические прогнозы на допустимом горизонте и видимые события; если у конкретного терминала нет соответствия плану, система показывает причину пропуска и не создаёт ложный прогноз.

## 4. Контракты данных

Существующий префикс backend API остаётся `/api/v1`; ML API остаётся `GET /health` и `POST /predict`. Новые поля добавлять через Pydantic-схемы с обновлением OpenAPI. Итоговые имена полей могут быть согласованы с существующими схемами до реализации, но их семантика и проверяемые требования ниже обязательны.

### 4.1. Пример события прогноза

```json
{
  "type": "prediction_update",
  "event_id": "pred-131672-2026-09-26T12:00:00Z",
  "emitted_at": "2026-09-26T12:00:01Z",
  "data": {
    "tr_id": 131672,
    "unit_id": 615932,
    "source": "live",
    "T": "2026-09-26T12:00:00Z",
    "produced_at": "2026-09-26T12:00:01Z",
    "target_stop_id": 8123,
    "target_time_begin": "2026-09-26T12:12:00Z",
    "predicted_delay_s": 143.5,
    "predicted_arrival": "2026-09-26T12:14:23.500Z",
    "current_delay_s": 74.0,
    "current_delay_source": "confirmed_stop",
    "model": "lightgbm_plan",
    "model_version": "release-id",
    "model_artifact_sha256": "sha256-value",
    "p_late": null,
    "risk": "high",
    "risk_source": "threshold",
    "freshness": "fresh"
  }
}
```

Пример иллюстрирует формат, а не заданные для проекта ID, веса или пороги. `predicted_arrival = target_time_begin + predicted_delay_s`. Все сетевые timestamp передаются с часовым поясом; внутри системы используется UTC, в UI время переводится в выбранную зону с её явной подписью.

### 4.2. Статусы без прогноза

Для машин без результата определить машинно-читаемую причину: `schedule_unmatched`, `no_target_in_horizon`, `insufficient_data`, `ml_unavailable`, `invalid_telemetry`, `stale`. Отсутствие прогноза не кодируется нулём секунд. HTTP-ошибки ручного запроса содержат код и человекочитаемое описание; массовый список машин показывает статус без массовых 500-ошибок.

### 4.3. Источники данных и режимы

`live` — NDTP с текущим планом; `replay` — исторический поток через TCP с логическими часами; `manual` — диагностический вызов API. Источник каждой записи хранится и виден в интерфейсе. В production-конфигурацию не монтируются `labels_test.csv`, фактические прибытия test/validate и диагностические данные, используемые для ретроспективной оценки.

## 8. Ограничения и решение спорных случаев

1. Разметка `validate` недоступна: нельзя использовать фактическое время её целевой остановки из иных копий файлов или выводить «локальную MAE validate». Скрытый результат подтверждается только платформой.
2. Если время NDTP, план и replay не могут быть однозначно приведены к одной шкале, прогноз не публикуется до устранения несоответствия; журнал содержит причину.
3. Если `cur_dev_s` в живом режиме не удаётся вычислить корректно, выбирается явный статус или отдельно оценённый fallback. Подстановка из табличной конкурсной точки допустима только для соответствующего офлайн-сценария.
4. Вероятность опоздания публикуется только после проверки калибровки. Цветовая категория при её отсутствии помечается как эвристика.
5. Для демо допускаются искусственный план и назначение терминалов, но они именуются демонстрационными и не используются для утверждений о работе на реальной сети.
6. PostgreSQL и существующие сервисы используются по необходимости. Выбор временного или постоянного хранения инцидентов должен быть явно указан; перезапуск не должен молча представляться как сохранение истории, если её нет.

## 9. Определение завершённости

**P0 завершён**, когда AT-01–AT-09 проходят на документированном окружении, конкурсный файл проверен, его официальный статус честно указан, а демонстрация показывает полный автоматический путь от TCP-пакета до карточки инцидента. Модель в контейнере и модель CSV идентифицированы и сопоставлены; отсутствие обязательных данных вызывает понятный отказ, а не ложный результат.

**Полное ТЗ завершено**, когда выполнены также P1-требования к вероятности, качеству информации для диспетчера и нагрузочному протоколу AT-10; документация отражает фактический запуск. P2 не входит в критерий готовности.
