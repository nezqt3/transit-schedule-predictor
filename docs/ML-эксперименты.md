## ML-метрики

Основная метрика соревнования — **MAE (Mean Absolute Error)** по прогнозируемой задержке транспортного средства в секундах.

Модель решает задачу регрессии и предсказывает:

```text
target_delay_s
```

где `target_delay_s` — фактическое отклонение от расписания на целевой остановке в горизонте **10–15 минут**.

### MAE

MAE показывает, на сколько секунд в среднем прогноз модели отличается от фактической задержки:

```text
MAE = mean(|факт − прогноз|)
```

Чем меньше MAE, тем точнее модель.

Например:

```text
Факт:      120 сек
Прогноз:   100 сек
Ошибка:     20 сек

Факт:      300 сек
Прогноз:   360 сек
Ошибка:     60 сек

Факт:      -40 сек
Прогноз:   -30 сек
Ошибка:     10 сек
```

Средняя абсолютная ошибка:

```text
MAE = (20 + 60 + 10) / 3 = 30 секунд
```

То есть модель в среднем ошибается на 30 секунд.

### Итоговый score соревнования

Организаторы преобразуют MAE в итоговый `score` от `0` до `1`:

```text
MAE      = mean(|факт − прогноз|)
mae_zero = mean(|факт|)

score = max(
    0,
    min(
        1,
        (mae_zero − MAE) / (mae_zero − MAE_TARGET)
    )
)
```

где:

* `MAE` — ошибка нашей модели;
* `mae_zero` — ошибка baseline, который всегда предсказывает задержку `0`;
* `MAE_TARGET` — целевое значение MAE, заданное организаторами;
* `score` — итоговая нормализованная оценка решения в диапазоне `[0, 1]`.

Таким образом:

```text
меньше MAE
    ↓
лучше прогноз
    ↓
выше score
```

Если модель не превосходит baseline `prediction = 0`, итоговый score стремится к `0`.

### Baseline

Перед обучением сложных моделей обязательно сравниваем результат с простыми baseline.

Минимальный baseline:

```python
prediction = 0
```

Также используем сильный baseline текущего отклонения:

```python
prediction = cur_dev_s
```

Основная задача CatBoost/PyTorch — получить MAE ниже baseline на временной валидации и итоговом leaderboard.

### Дополнительные метрики

Внутри экспериментов дополнительно можем отслеживать:

* RMSE — для анализа крупных ошибок;
* median absolute error — для понимания типичной ошибки;
* MAE по отдельным маршрутам/ТС;
* MAE по различным горизонтам прогноза;
* precision/recall критических задержек — для диспетчерского интерфейса.

Однако **основной метрикой качества ML-модели и оптимизируемой метрикой соревнования является MAE в секундах**.

Валидация должна учитывать временную природу данных: признаки для момента `T` строятся только из информации, доступной на момент `T` или раньше. Использование будущей телеметрии приводит к target leakage и некорректной оценке MAE.

## Предобработка данных

Сырые данные соревнования содержат много артефактов NDTP-выгрузки. Весь clean живёт в
[`ml/src/preprocessing.py`](ml/src/preprocessing.py), запускается одной командой из корня:

```bash
python scripts/preprocess_data.py
```

Результат — очищенные таблицы в `data/processed/` и machine-readable отчёт
`data/processed/preprocessing_report.json` со счётчиками по каждому правилу.
В отчёте также есть постфактум-снимок качества: `missing_after` (доли пропусков
после clean: lat/lon 7,4%, speed 5,9%, gps_time 56,2% в train), `tr_id_count`,
границы `event_time_min/max` и статистика target (`mean` 48,9 / `median` 24 /
`std` 131,2 на train против 55,7 / 26 / 135,5 на test — распределения
согласованы).
Логика одна для train и test, инференс использует те же правила — расхождений
«kaggle-код vs прод-код» нет.

Отдельная находка: `data/raw/test/traffic.csv` и `data/raw/validate/traffic.csv`

### Что починили в расписании

- WKT `geom` разбирается в числовые `stop_lon` / `stop_lat` (100% парсятся);
- появляется `dev_s = time_fact_begin − time_begin` — фактическое отклонение
  на остановке, тот же смысл, что и целевой `target_delay_s` (в train-расписании
  от −404 до +685 с, выбросов за 30 минут нет);
- пустой `building_address` (2 925 строк, 17,5%) → пустая строка, пропуск не
  мешает groupby-фичам по остановке;
- `manual_fill` и datetime-колонки (в train — наносекундный формат без
  разделителя) приводятся к нормальным типам.

### Проверки меток

`labels_train` (4 434) и `labels_test` (353) оказались чистыми: дублей нет,
пропусков target нет, контракт горизонта `(T+10; T+15]` минут соблюдается для
всех строк — проверки в `preprocess_labels` зафиксированы как guard от будущих
регрессий, target_delay_s лежит в `[−372, +672]` — регрессия, не классификация.

Контроль sanity на clean-данных: baseline-предиктор `prediction = cur_dev_s`
даёт MAE 93,0 с на train и 93,4 с на test — распределения согласованы,
ориентир, который модель обязана перебить.

### Итог

После clean: телеметрия отсортирована по `(tr_id, event_time)`, дублей
времен нет, все числовые поля в физических диапазонах, у каждой строки есть
или валидные координаты, или честный NaN через `coords_valid`. Признаки
строятся только из `event_time <= T`, так что leakage-поверхность после
препроцессинга закрыта.

### ML-эксперимент: archive vs live (`scripts/exp_catboost_archive.py`)

Archive/live — фактически два режима источника данных, и распределены они
асимметрично: 74,3% train-семплов имеют archive-пакет последним перед T,
тогда как в test archive-строк нет вообще (0%). CatBoost (loss MAE, early
stopping на хвосте train по времени, оценка MAE на labels_test):

| Модель | Данные | MAE test |
| --- | --- | --- |
| baseline `cur_dev_s` | — | 93,36 |
| A | фичи из archive + live | 85,50 |
| B | фичи только из live | 84,74 |
| C | A + признаки `is_archive_last` / `archive_frac_5m` | **83,70** |

Paired-сравнение по 353 test-семплам: C лучше A на 1,80 с (t=−2,9), B лучше A
на 0,76 с (t=0,9 — незначимо). Вывод: прятать archive из train не нужно, но
режим источника стоит явно отдавать модели как признак — с ним модель сама
решает, какие паттерны переносимы в live-домен, и это лучший вариант из трёх.
`cur_dev_s` остаётся доминирующим признаком (importance 42–49%), остальные
фичи дают ~8–10 с поверх baseline.

### ML-эксперименты D/E/F/G поверх C (`scripts/exp_models_defg.py`)

Чемпион C (83,70) прогнан через четыре варианта; оценка MAE на labels_test,
контрольная сверка — на time-tail валидации внутри train (последние 15% по T):

| Модель | Изменение | MAE test | Δ vs C (paired t) |
| --- | --- | --- | --- |
| C | чемпион | **83,70** | — |
| D | без категориального `tr_id` | 84,88 | +1,18 (t=1,2, незначимо) |
| E | target = `target_delay_s − cur_dev_s` (residual) | 87,95 | +4,26 — явно хуже |
| F | + динамика: std/delta по половинкам окна, stopped_ratio, distance_travelled, `required_speed_kmh`, `speed_vs_required_kmh`, `cur_dev_per_time_to_stop` | 84,05 | +0,36 (незначимо) |
| G | сетка гиперпараметров поверх F | 82,25 | −1,45 (t=−2,3) |

Вердикт по честному:

- **D** — `tr_id` полезен, оставляем;
- **E** — residual-таргет хуже прямой регрессии: CatBoost и так сильно опирается
  на `cur_dev_s`, а двухступенчатая схема только размывает сигнал;
- **F** — «успевает ли ТС физически» (`required_speed`, `cur_dev_per_time_to_stop`)
  набрал ~28% importance, **но MAE не улучшил** — признаки релевантны по смыслу,
  их информация уже частично покрыта `cur_dev_s` + `dist_to_stop_m` + `time_to_stop_s`;
- **G** — 82,25 на test **не воспроизвелось** на time-tail валидации train
  (79,5 против 78,6 у конфигурации C): выигрыш получен выбором лучшего из 16
  конфигов по 353 test-семплам, то есть selection-on-test. Это не принимаем
  за реальный прирост.

Текущий чемпион для submission остаётся **C**; ideas на будущее — не тюнинг по
маленькому test, а больше скорельных признаков истории задержек самого ТС
(средняя/медианная задержка `tr_id` на этой остановке по train-дням).

### ML-эксперименты H/I: окружение сегмента и seed-ensemble (`scripts/exp_segment_ensemble.py`)

**H** добавляет к C признаки участка (ячейка сетки ~500 м, где сейчас ТС,
только пакеты `event_time <= T`): `segment_speed_mean/median_5m` по всем ТС в
ячейке, `segment_vehicle_count_5m`, `segment_stopped_ratio_5m`,
`historical_segment_speed` (накопленное среднее сегмента до T), ratios
`vehicle_vs_segment_5m`, `segment_vs_historical_5m` и класс schedule pressure:
`speed_deficit_mean_1m/3m`, `schedule_pressure = required_speed / segment_speed`,
`required_vs_historical` — «надо 36 км/ч, а участок едет 14».

**I** — ансамбль CatBoost на 5 сидах (42/1337/2026/777/123), агрегация mean и
median, плюс измерение seed-дисперсии одиночных моделей:

| Модель | MAE test | vs C (paired) |
| --- | --- | --- |
| C single (seed=0, «чемпион») | 83,70 | — |
| H single (seed=0) | **83,53** | −0,17 (t=−0,3) |
| HF (H + динамические фичи F) | 83,99 | +0,30 |
| I: C ensemble mean / median | 84,42 / 84,34 | +0,73 / +0,65 |
| I: H ensemble mean / median | 83,76 / 83,87 | +0,07 / +0,18 |

Главный честный вывод: **разброс по сидам больше, чем различия моделей**.
C по шести сидам даёт MAE 83,7–85,4 (mean 84,5, std 0,7) — «чемпионские» 83,7
были самым удачным сидом; H даёт 83,4–84,6 (mean 83,9, std 0,5). По среднему
по сидам H стабильно лучше C примерно на 0,6 с, и `historical_segment_speed`
вошёл в топ-6 важности — признаки окружения работают, но на 353 строках test
каждое отдельное сравнение в пределах шума.

Решение для submission: **H + mean-ensemble из 5 сидов** (медиана на MAE здесь
не лучше средней, при этом ансамбль убирает luck-of-the-seed), ожидаемо
честный уровень ~83,8–84,0.

### ML-эксперименты J / blend / error analysis (`scripts/exp_blend_errors.py`)

**J** = фичи F+segment вместе, обученные с параметрами G (`l2_leaf_reg=1`,
`random_strength=1`). Веса гетерогенного blend G/H/C подбирались на time-tail
OOF (хвост последних 15% train-labels), `labels_test` трогался ровно один раз.

| Модель | OOF tail MAE | test MAE |
| --- | --- | --- |
| C | 81,04 | 83,70 |
| G | 79,53 | **82,25** |
| H | 79,80 | 83,53 |
| J | **78,43** | 83,39 |
| blend 0.6G+0.4H (веса по OOF) | 79,38 | 82,69 |

Честная интерпретация: по OOF лучший — **J в одиночку** (blend из G/H/H ему
проигрывает, 79,4 против 78,4). На test разброс J 83,4 vs G 82,3 лежит внутри
seed-стандарта ~0,6 — выбор по одному test числу ненадёжен. Для submission:
**J + mean-ensemble из 5 сидов** (лучший по OOF + устойчивый к сид-шуму).

**Error analysis J/G по структуре ошибок** (разложение MAE модели G на test):

| Срез | Где боль |
| --- | --- |
| target | `very_late>180` (55 семплов) — MAE 198, **37,6% всей ошибки**; `early<−60` (50) — MAE 121, ещё 20,8%; обе хвостовые группы = ~58% ошибки при 30% строк |
| horizon | основная масса (225 из 353) в бакете 10–11 мин, MAE 75,5 — тут всё ок; редкие дальние бакеты 12–13 и 14–15 шумят (MAE 103/128 при n=20/10) |
| cur_dev | даже при «спокойном» cur_dev −60..60 MAE 68,9 — модель якорится на cur_dev и не видит надвигающуюся катастрофу |
| distance | MAE растёт с дистанцией: 76,6 (<1км) → 84,7 (1–3км) → 94,1 (3–5км) |

**Топ-20 худших объектов** (21,3% всей суммы |ошибок|) дают явный паттерн:

- средний signed error **−228 с** — модель систематически **недопредсказывает**
  большие опоздания (MAE-лог обучает на медиану, хвосты режет);
- 4 кейса вида `cur_dev_s≈59, target≈550`: ТС ещё почти в графике, но
  `stopped_ratio_5m` 0.9+ и скорость сегмента 0,3–1,3 км/ч утром в 7:00 —
  затор уже стоит, а модель не решается предсказать коллапс. Признаки были
  в фичах — их перевешивает якорь `cur_dev_s`;
- 7 из 20 ошибок — один `tr_id` 122048 (7:00–7:40 утра): рейсовые/личные
  паттерны конкретного ТС не учтены;
- ночные опоздания (h≈3:00, `cur_dev` уже 240–320, сегмент пуст и speed 35 км/ч) —
  это позднее начало рейса, а не трафик: не хватает признака «задержка на старте рейса»;
- early-хвост (target −260..−280 при cur_dev ~0) — модель вообще не умеет
  предсказывать «приедет раньше», жмёт к нулю.

Отсюда следующий feature (важнее нового grid search): **dev-trend** — фактическая
задержка ТС на последних пройденных остановках рейса и её наклон
(сек задержки/мин), считается только по событиям ≤ T из склейки телеметрии с
плановыми `time_begin` тех же рейсов; плюс **start_delay** (насколько ТС
вышло с начальной остановки позже плана) и конвейерные/quantile признаки
для хвостов. Ожидаем удар именно по very_late/early — 58% остаточной ошибки.

### ML-эксперимент K: incident precursor features (`scripts/exp_precursor_k.py`)

Две группы «предсигналов» поверх J (всё строго `event_time <= T`):

- **короткая динамика**: `speed_mean_30s`, ratios `30s/5m` и `1m/5m`,
  `speed_drop_1m/3m/30s`, `speed_trend_1m/3m` (МНК-наклон км/ч/мин),
  `acceleration_mean/min` — различить «ехал 30, сейчас 28» (шум) и
  «32→27→16→7» (сбой развивается);
- **forward-корridor**: состояние чужого ТС на отрезке «наше ТС → целевая
  остановка» (проекция на линию A→B, коридор 250 м, последние 5 мин):
  `next_segment_speed_mean` (ближайшая треть), `next_2/3_segments`,
  `vehicles_ahead_*`, `next_segment_congestion_ratio`,
  `distance_to_slow_traffic_m` — увидеть проблему до появления задержки.

| Модель | OOF tail (mean-ens) | test (5 seeds, mean-ens) | seed-std |
| --- | --- | --- | --- |
| J (45 фич) | 79,45 | 83,75 | 0,78 |
| K = J + precursor (66 фич) | 79,80 | **83,65** | 0,54 |

Paired K vs J: Δ = −0,11 с (t = −0,23) — **внутри seed-шума, общего выигрыша
нет**. Но важность в K-модели честная: `next_segment_stopped_ratio` (2,3) и
`next_segment_congestion_ratio` (1,7) — в топ-10 фич, `vehicles_ahead_mean_speed`
тоже попадает в топ-15. То есть corridor-сигнал модель использует, но на общем
MAE из 353 строк он тонет; его место — риск-скоринг и very_late-подвыборка
(см. regime ниже). **Champion-фичи: K** (не хуже J, добавляет объяснимые
сигналы инцидентов, seed-шум меньше).

### Regime model: P(very_late), P(early) с OOF-вероятностями (`scripts/exp_regime.py`)

Два CatBoost-классификатора на том же K-наборе: `is_very_late = target > 180`,
`is_early = target < −60`. Вероятности для стекинга — только walk-forward OOF
(5 chronological-фолдов: модель на фолдах 0..i−1 предсказывает фолд i), test —
один раз.

| Сигнал | OOF AUC (фолды) | test AUC | top-decile precision на test |
| --- | --- | --- | --- |
| p_very_late | 0,775 | **0,875** | pos rate 0,49 при base 0,156; mean target 174 с |
| p_early | 0,723 | **0,874** | pos rate 0,49 при base 0,142; mean target −54 с |

Децили p_very_late монотонны: mean target от −25 с (низший дециль) до +174 с
(высший), т.е. это готовый **risk-сигнал дашборда** («инцидент вероятен» ещё до
роста cur_dev). Как **дополнительный признак регрессора стекинг не работает**:
tail MAE 81,91→81,57 (плюс), но test 76,59→77,83 (Δ +1,24, t = 1,84 — минус):
полно-данные test-вероятности смещены относительно OOF-вероятностей в обучении
(архив/live сдвиг). Решение: классификаторы — в инцидент-контур и фичи
дашборда, в регрессию их не стекаем.

### ML-эксперимент: PyTorch GRU на траектории (`scripts/exp_gru.py`)

GRU получает поминутную траекторию скорости за 5 минут до T (5 шагов:
средняя скорость в бакете + флаг наличия данных) плюс скаляры `cur_dev_s`,
`time_to_stop_s`, `current_speed`, `gap_since_last_pkt`; loss L1, ранняя
остановка на time-tail, mean-ensemble из 3 сидов.

| Модель | tail OOF MAE | test MAE |
| --- | --- | --- |
| CatBoost K (3 сида) | 79,72 | **83,73** |
| GRU | 79,71 | 85,01 |
| blend α·GRU+(1−α)·CatBoost, α=0,5 по tail | **78,83** | 83,51 |

Выводы честные: один GRU не быстрее CatBoost (разрыв +1,3 с на test при
t = 0,64), но кривая α на tail **монотонно** улучшает MAE до 78,8 — у модели
на траектории реально независимые ошибки (гипотеза подтвердилась частично:
на фокусной подвыборке very_late с нормальным cur_dev, n=14, GRU не лучше —
14 строк, только шум). Для submission можно брать blend α≈0,3–0,5: tail-уверенность
высокая, test-улучшение в пределах шума (t = −0,21). Это первый кандидат в
вторую модель продакшн-контуре (ансамбль разнородных моделей).
