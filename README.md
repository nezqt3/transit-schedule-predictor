# МСК Хакатон транспорта — прогнозирование задержек общественного транспорта

Проект команды для **МСК Хакатона транспорта**. Решение собирает телеметрию транспортных средств, объединяет её с расписанием и строит прогноз задержки рейса или прибытия на целевую остановку.

> Статус: MVP-каркас. Основные контуры репозитория разложены, ML- и сервисные точки входа подготовлены для дальнейшей реализации и обучения.

## Бизнес-идея

Городской транспорт теряет время и деньги не только из-за пробок, но и из-за того, что диспетчер видит проблему уже после возникновения задержки. Наша задача — превратить поток телеметрии в раннее предупреждение:

```text
телеметрия ТС + расписание + история отклонений
                    ↓
          признаки текущего рейса
                    ↓
       ML-прогноз задержки и класса
                    ↓
 диспетчер / пассажирский сервис / аналитика
```

### Что получает транспортный оператор

- заранее видит рейсы, которые с высокой вероятностью выйдут из расписания;
- может перераспределить резервный транспорт и водителей до того, как проблема станет массовой;
- получает единый слой данных для контроля маршрутов, остановок и фактического исполнения расписания;
- сокращает ручной разбор телеметрии и постфактум-отчётность;
- может оценивать качество маршрутов по фактической задержке, а не только по плану.

### Что получает пассажир

- более точное ожидаемое время прибытия;
- предупреждение о задержке до поездки;
- меньше неопределённости при пересадках и выборе маршрута.

### Экономический эффект: «что по чём»

На этапе хакатона мы не подменяем реальные расчёты выдуманной экономией. Модель эффекта считается от данных оператора:

| Показатель | Как считаем | Зачем нужен |
| --- | --- | --- |
| средняя задержка | фактическое время − плановое время | базовая линия качества |
| доля опоздавших рейсов | рейсы выше порога / все рейсы | масштаб проблемы |
| раннее предупреждение | время до фактической задержки | полезность прогноза |
| precision/recall по критическим задержкам | прогноз против labels | качество ML |
| стоимость инцидента | простой, штрафы, жалобы, сорванные пересадки | деньги оператора |
| экономия | предотвращённые инциденты × стоимость одного инцидента | ROI внедрения |

Коммерческая модель после пилота: SaaS/API для транспортного оператора или городского интегратора с оплатой за парк, маршрут или объём обработанной телеметрии. Дополнительные продукты — аналитика исполнения расписания, мониторинг SLA и пакет прогнозов для пассажирского приложения.

## Как работает решение

1. NDTP-эмулятор отправляет телематические пакеты: координаты, скорость, курс, датчики и идентификатор борта.
2. Backend принимает поток, разбирает NPL/NPH-пакеты и предоставляет API транспортных объектов.
3. ML-контур объединяет traffic, schedule и labels, строит временные и маршрутные признаки.
4. CatBoost и PyTorch обучаются на исторических данных; ансамбль объединяет прогнозы.
5. FastAPI ML-сервиса возвращает секунды задержки, класс задержки и версию модели.
6. Результат может использоваться диспетчерским интерфейсом, уведомлениями и отчётами.

## ML-метрики

Основная метрика соревнования — **MAE (Mean Absolute Error)** по прогнозируемой задержке транспортного средства в секундах.

Модель решает задачу регрессии и предсказывает:

```text
target_delay_s
```

где `target_delay_s` — фактическое отклонение от расписания на целевой остановке в горизонте **10–15 минут**.

### MAE

MAE показывает, на сколько секунд в среднем прогноз модели отличается от фактической задержки:

```text
MAE = mean(|факт − прогноз|)
```

Чем меньше MAE, тем точнее модель.

Например:

```text
Факт:      120 сек
Прогноз:   100 сек
Ошибка:     20 сек

Факт:      300 сек
Прогноз:   360 сек
Ошибка:     60 сек

Факт:      -40 сек
Прогноз:   -30 сек
Ошибка:     10 сек
```

Средняя абсолютная ошибка:

```text
MAE = (20 + 60 + 10) / 3 = 30 секунд
```

То есть модель в среднем ошибается на 30 секунд.

### Итоговый score соревнования

Организаторы преобразуют MAE в итоговый `score` от `0` до `1`:

```text
MAE      = mean(|факт − прогноз|)
mae_zero = mean(|факт|)

score = max(
    0,
    min(
        1,
        (mae_zero − MAE) / (mae_zero − MAE_TARGET)
    )
)
```

где:

* `MAE` — ошибка нашей модели;
* `mae_zero` — ошибка baseline, который всегда предсказывает задержку `0`;
* `MAE_TARGET` — целевое значение MAE, заданное организаторами;
* `score` — итоговая нормализованная оценка решения в диапазоне `[0, 1]`.

Таким образом:

```text
меньше MAE
    ↓
лучше прогноз
    ↓
выше score
```

Если модель не превосходит baseline `prediction = 0`, итоговый score стремится к `0`.

### Baseline

Перед обучением сложных моделей обязательно сравниваем результат с простыми baseline.

Минимальный baseline:

```python
prediction = 0
```

Также используем сильный baseline текущего отклонения:

```python
prediction = cur_dev_s
```

Основная задача CatBoost/PyTorch — получить MAE ниже baseline на временной валидации и итоговом leaderboard.

### Дополнительные метрики

Внутри экспериментов дополнительно можем отслеживать:

* RMSE — для анализа крупных ошибок;
* median absolute error — для понимания типичной ошибки;
* MAE по отдельным маршрутам/ТС;
* MAE по различным горизонтам прогноза;
* precision/recall критических задержек — для диспетчерского интерфейса.

Однако **основной метрикой качества ML-модели и оптимизируемой метрикой соревнования является MAE в секундах**.

Валидация должна учитывать временную природу данных: признаки для момента `T` строятся только из информации, доступной на момент `T` или раньше. Использование будущей телеметрии приводит к target leakage и некорректной оценке MAE.


## API-контуры

Backend отвечает за приём и выдачу транспортных данных. ML-сервис предоставляет:

```text
GET  /health
POST /predict
```

Формат запроса и ответа будет закреплён в `ml/service/schemas.py`. Версия модели должна возвращаться в ответе, чтобы результат можно было воспроизвести и сравнить.
