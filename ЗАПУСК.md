# Запуск и проверка демонстрации

## 1. Что сдаётся и какая модель работает

- Конкурсный файл: `data/submissions/final_submission.csv` — **151 строка**, формат `sample_id;prediction`. Проверка: `python scripts/verify_submission.py`.
- ML в Compose: **LightGBM plan**, версия `lightgbm-plan-2026-09-26`. Манифест и SHA-256 весов: `ml/artifacts/release_manifest.json`. При отсутствии или повреждении весов сервис не подменяет модель на baseline.
- Локальная MAE на 353 размеченных test-точках: **58,6033 с** против **93,3598 с** у `cur_dev_s`; временная CV на train — **76,4503 с**. По сообщению команды LightGBM получил на платформе **score 1 = 1 (максимум)**; ссылка/скрин конкретной отправки пока не приложены, поэтому соответствие хешу текущего CSV документально не подтверждено.
- Дополнительная вероятность опоздания ≥120 с калибрована на временных OOF-прогнозах. Brier score на test: **0,1010** против **0,1847** у постоянной частоты. Подробности в `ml/artifacts/risk_calibration.json`.

Регрессионный ответ модели — отклонение в секундах: положительный знак означает опоздание, отрицательный — опережение. Вероятность и цвет риска не заменяют основной конкурсный прогноз.

## 2. Запуск из checkout

Нужны Docker Compose и файлы `data/raw/validate/{traffic.csv,schedule_plan.csv}`. Исторический replay дополнительно использует `data/raw/validate/points.csv`. Базовый Compose монтирует только план и файл соответствия терминалов; опубликованные входные точки и test-разметка доступны только явному диагностическому overlay. Выбранные веса в `ml/artifacts/` и конкурсные CSV включены в текущую конфигурацию репозитория; их SHA-256 сверяется при загрузке ML. Девять исходных CSV уже отслеживаются в Git; команда подтвердила, что пока это единственный общий источник. Они оставлены для воспроизводимого checkout, новые raw-файлы игнорируются. После публикации отдельного архива с хешами существующие CSV можно убрать из будущих коммитов.

```bash
cp .env.example .env
docker compose up --build
```

Открыть `http://localhost:8080`, войти демо-учётной записью `dispatcher` / `transport`. Для любого внешнего размещения перед запуском изменить пароль и `AUTH_JWT_SECRET` в `.env`.

| Адрес | Назначение |
|---|---|
| `http://localhost:8080` | диспетчерский интерфейс |
| `http://localhost:8000/docs` | текущий Swagger/OpenAPI backend |
| `http://localhost:8000/api/v1/health` | здоровье backend |
| `http://localhost:8001/health` | загруженная модель, версия и хеш |
| `localhost:9201` | TCP NDTP |

Команда `docker compose up --build` запускает систему и **ожидает NDTP-пакеты**. Прогнозы появятся после подключения потока с расписанием или в явном демо-режиме ниже. Доступные состояния отсутствия прогноза показываются в API `/api/v1/predictions/statuses` и карточке терминала.

## 3. Прогон исторического NDTP через TCP

Это архивная запись с конкурсным планом и опубликованными входными точками `cur_dev_s`. Она запускает тот же автоматический backend-контур через TCP, а не ручной вызов `/predictions`.

```bash
make up-dataset-replay
```

Скрипт выбирает до двух машин с расписанием, включает исходные январские timestamps и по умолчанию ускоряет **подачу** в 1800 раз. Время пакета и план не масштабируются, поэтому целевой горизонт остаётся `(T+10 мин, T+15 мин]` в логических часах записи. На экране поток помечен как «Исторический NDTP · архив»; он не изображает текущую обстановку города.

В PowerShell выбор конкретных машин и скорости выглядит так:

```powershell
$env:REPLAY_TR_IDS = '131672,122048'
$env:REPLAY_SPEED = '1800'
python scripts/start_dataset_replay.py
```

Статус подачи: `http://localhost:18081/api/status`. Успешный путь: растут `accepted_packets` в `/api/v1/metrics`, появляются `/api/v1/predictions`, `/api/v1/incidents`, а в WebSocket `/api/v1/ws` идут `vehicle_update`, `prediction_update`, `incident`. Последняя запись содержит `source=replay` и `current_delay_source=point_input`, если опубликованный вход `cur_dev_s` известен на текущем `T`; иначе используется GPS-подтверждение уже пройденной остановки. Эти источники не смешиваются молча.

Дополнительный табличный раздел «Исторический прогон» доступен через переключатель источника в интерфейсе при запуске с `docker-compose.replay.yml`. Он предназначен для ретроспективного сравнения. Общий ответ `/api/v1/replay/fleet` не содержит будущий `actual_delay_s`; факты запрашиваются через `/api/v1/replay/outcomes` только по уже наступившему времени воспроизведения. Backend ограничивает клиентский `as_of` текущими часами NDTP replay: дата из будущего не раскрывает будущий исход.

## 4. Эмулятор организаторов

Для запуска нужен предоставленный организаторами Docker-образ с точным путём
`emulator/ndtp-telemetry-emulator.tar`. Он не входит в Git. Другой путь можно
передать через `make up-ndtp NDTP_EMULATOR_ARCHIVE=/полный/путь/ndtp-telemetry-emulator.tar`.

```bash
make up-ndtp
```

Команда включает отдельный Compose overlay `docker-compose.official-demo.yml` и подключает два терминала из `emulator/official-demo-config.json`. Эмулятор создаёт синтетические GPS-точки и **не передаёт реальный рейс или план**. Поэтому backend строит отдельный явно помеченный синтетический план и принимает заданное демо-отклонение 1000 с. В API и карточке такие результаты имеют `source=demo`, `current_delay_source=demo_anchor`. Они доказывают прохождение TCP → parser → ML → инцидент → UI, **но не качество на реальном городском расписании**. Скрипт после подачи ждёт прогнозы и инциденты для обоих терминалов; если их нет, завершится ошибкой с подсказкой открыть `/api/v1/predictions/statuses`.

## 5. Проверка API и модели

Вход выполняется OAuth2 **form**, не JSON:

```bash
curl -c cookies.txt -X POST http://localhost:8000/api/v1/auth/token \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'username=dispatcher&password=transport'
curl -b cookies.txt http://localhost:8000/api/v1/predictions
curl -b cookies.txt http://localhost:8000/api/v1/incidents
curl -b cookies.txt http://localhost:8000/api/v1/metrics
```

Локальные проверки без Docker:

```bash
python scripts/verify_submission.py
python scripts/verify_model_parity.py
python scripts/evaluate_risk_policy.py
cd backend && python -m pytest -q
cd ../ml && python -m pytest -q
cd ..
pnpm -C frontend build
python scripts/export_openapi.py
```

`verify_model_parity.py` проверяет все 353 test-точки через HTTP `/predict` и сравнивает ответы с сохранёнными офлайн-признаками. Разметка test используется только в этой локальной проверке, не монтируется в стандартный production/backend Compose. Опциональный overlay `docker-compose.replay.yml` монтирует её исключительно для диагностического исторического раздела.

## 6. Нагрузка и устойчивость

Нагрузочный профиль создаёт **отдельное синтетическое расписание** для 100 терминалов; результаты нельзя трактовать как проверку точности модели на реальном маршруте.

```bash
python scripts/benchmark_ndtp.py --prepare --units 100
docker compose -f docker-compose.yml -f docker-compose.benchmark.yml up -d --build
python scripts/benchmark_ndtp.py --units 100 --duration-s 600 --interval-s 15 --report data/processed/benchmark/report.json
```

По умолчанию терминалы имеют равномерно распределённые фазы отправки: каждый отправляет пакет каждые 15 секунд. Флаг `--synchronized` проверяет отдельный стрессовый сценарий одновременного залпа. Отчёт содержит число отправленных/принятых пакетов, потери, успешные прогнозы и p50/p95/p99 от отправки TCP-пакета до WebSocket-события. Цель ТЗ: p95 ≤2 с, без роста очереди и потери корректных пакетов. Фактические цифры и машинный отчёт финальной сборки приведены в `docs/ПРОТОКОЛ-приёмки.md` и `docs/benchmarks/at10-final.json`.

Compose запускает `ML_WORKERS=4` CPU-процесса модели; backend допускает до `ML_MAX_IN_FLIGHT=8` одновременно отправленных запросов. Эти параметры можно изменить в `.env` под доступные CPU и память. Синхронный залп из 100 машин на одном процессе ML давал p95 около 4,8 с; с четырьмя процессами и ограниченной очередью короткий залп дал p95 1,344 с без потерь.

При остановке ML backend продолжает принимать NDTP и помечает прежний прогноз устаревшим; повторный вызов ML ограничен паузой. При разрыве WebSocket интерфейс восстанавливает состояние через REST. При недоступности PostgreSQL вход временно закрыт, backend повторяет подключение без перезапуска.

## 7. Документация и ограничения

- Живые OpenAPI: `http://localhost:8000/docs`, `http://localhost:8000/openapi.json`.
- Статическая схема: `docs/public/api.html`, `docs/public/openapi.json`; краткая Sphinx-документация: `docs/public/pydoc/index.html`.
- ТЗ и сценарии приёмки: `docs/ТЗ-доработки-системы.md`.
- Манифест качества и веса: `ml/artifacts/release_manifest.json`.

Состояние прогнозов и инцидентов хранится в памяти backend и сбрасывается при перезапуске. PostgreSQL сейчас используется для авторизации. Утверждение о постоянной истории инцидентов до добавления отдельного хранилища недопустимо. Для независимой проверки сообщения команды об официальном балле нужен артефакт платформы, связывающий результат с конкретной отправкой CSV.
